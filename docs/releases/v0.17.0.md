# v0.17.0

v0.17.0 saves a list of recipients under a name, lists what the fetch
kept as damaged and reopens what needed a newer `auu`, and stops the key
agent when its socket is replaced. It needs no upgrade order from
v0.15.0 or v0.16.0: nothing it sends is new, and the relay, `auu-admin`,
the wire level and the relay's schema are as v0.16.0 left them. The wire
level stays 1 and the schema stays 13.

## What changed

**Rooms.** A room is a list of recipients saved under a name, kept in
`rooms.json` in the home. `auu room create team bob carol` makes one,
and `auu room ls`, `show`, `add`, `rm` and `delete` keep it. A member is
yourself, a peer, or a peer at an address, `'bar!dave'`, whose relays
the room keeps. `auu send --to team` sends one message to everyone in
the room, as `--to bob,carol` would, and a room mixes with names. A room
is matched by its whole name in any case, never by a prefix. A prefix
that is not also a room's whole name still reaches the peer it always
reached. A room and a peer may not share a name. Everything about a send
to a room is checked before anything is sealed: `--via` beside a room is
refused, and so is a member no longer on the peer list, somebody reached
twice through rooms and names, and more recipients than 32 or than the
relay takes once the room is counted. A room of one is a message to one.

Nothing of a room is posted. A relay never learns that one exists, and
recipients see a message to several and who it went to, never the
room's name. `auu read`, `auu wait` and `auu quarantine show` print
`room:` with a room's name when the other people on a message to
several are exactly that room's members. That is this machine's own
label, and `--json` carries it as `room`. A second machine of the same
identity has its own rooms, as it has its own peer list.

**`auu damaged ls` and `auu damaged reopen`.** `auu damaged ls` lists
what the fetch kept under `damaged/`: the relay, the relay's id, when it
arrived, its size and its cause. `auu damaged reopen RELAY ID`, or
`--all`, opens a message kept as needing a newer `auu` once `auu` is
updated. It runs the fetch's own checks and files what opens where the
fetch would have. It fetches and acknowledges nothing, and it opens no
other cause. As after a fetch, it may then answer a peer's request for a
vouch. From this release the record of such a message says the kind,
channel, relays and size the relay listed it with, so reopening can run
the checks against the listing. A record an earlier release wrote does not,
and reopen says which checks could not run.

**The key agent stops when its socket is replaced.** An agent already
stopped when its socket or its runtime directory was removed. It now
also locks and stops when another file, or another agent's socket,
stands at its path, or when its runtime directory has become a file.
Stopping, it removes nothing that is not its own socket, where it used
to remove whatever stood at the path.

**The documents are held to the programs.** Every `auu`, `auu-admin`,
`auu-ca` and `auu-relay` command a guide, the README or a release note
shows is checked against the programs by the tests, as the skills'
commands already were.

## From v0.15.0 or v0.16.0

There is no order. Upgrade the relay and the clients in any order, one
at a time, and send from an upgraded machine at once. v0.17.0 sends what
v0.16.0 sends, so the compatibility of v0.16.0 with v0.15.0, in
[`docs/releases/v0.16.0.md`](v0.16.0.md), holds for v0.17.0 unchanged. A
message to a room is a message to several on the wire. A v0.16.0 `auu`
reads it whole and names everyone it went to. A v0.15.0 `auu` reads it
as a plain message from the sender.

A rooms file is new, and an earlier `auu` does not read it. An earlier
`auu` on the same home reads a room's name as a peer's, so `--to team`
there reaches a peer of that name, or whose name begins with it, and
nobody else. A peer added by an earlier `auu` on the same home may take
a room's name. A send to that name is then refused, naming both, until
one of the two goes.

## From v0.14

Go straight to v0.17.0, in one step. v0.15.0 and v0.16.0 need never be
installed. The floor is the wire v0.15.0 set, and v0.17.0 speaks it. The
order is v0.15.0's, for the reasons
[`docs/releases/v0.15.0.md`](v0.15.0.md) gives, with v0.16.0's one
exception, a large message to several, below. The relay's database is
schema 13 on v0.14, v0.15.0, v0.16.0 and v0.17.0 alike.

**The relay first, with `auu-admin`,** if it is still on v0.14. A
v0.17.0 `auu`, like v0.15.0's, refuses a v0.14 relay's health answer,
which lacks `wire_level`. A v0.14 `auu-admin` misreads a v0.17.0 relay's
answers about one mailbox and a newly added token, as it does v0.15.0's.

**Then each party, in turn, drains its inbox and upgrades.** Drain with
`auu inbox` while still on v0.14, then install v0.17.0.

**A party that has upgraded may send at once,** except a large message
to several to anybody still on v0.14. That includes a large message to a
room with somebody still on v0.14 in it. v0.14 reads a stream's manifest
strictly, so it refuses one that carries a section, as every stream to
several does. It keeps the manifest under `damaged/` as malformed,
acknowledges it, so it is gone from the relay, and says to ask the sender
to send it again. Send that once the recipient has upgraded. Every other
message v0.14 reads as it reads v0.15.0's, and a message to several that
is not a stream reads there as a plain message from the sender.

**A party still on v0.14 holds its sends** to anyone who may have
upgraded, until it has upgraded too. v0.17.0, like v0.15.0, refuses a
message v0.14 sealed as malformed, saying "the sealed record carries no
version".

**A message refused in the window** is not lost. The machine that
refused it keeps it under `damaged/`, and it is sent again once its
sender has upgraded, or, for a large message to several, once its
recipient has. Once upgraded, `auu damaged ls` lists what was kept so.
