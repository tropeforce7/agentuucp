# v0.20.0

v0.20.0 adds `auu handle`, a host's scripts run on the asks to a
channel: a file of routes and its check, a service that runs each ask's
script in a directory of its own and replies to every ask it handles, its
limits and cleanup, and the operator's commands to look at its jobs and
move them. [`docs/handle.md`](../handle.md) is its guide, a systemd unit
for an account of its own among it. The wire level stays 2
and the relay's schema stays 13, so a v0.20.0 party and a v0.19.0 one are
the same party, and everything [`docs/releases/v0.18.0.md`](v0.18.0.md)
says about upgrading holds for v0.20.0 as it is.

## What changed

**`auu handle check` reads `handle.json` and says what it would run.**
`handle.json` in the home, or the file `--config` names, is a table of
routes keyed by id, each naming a channel and a command to run on the asks
that arrive there, with how it runs, its retries and its limits. `auu
handle check` holds the file to every rule
[`docs/handle.md`](../handle.md) gives and prints each route: its
channel, its command as written, its program as resolved, its jobs'
directory and its limits with the defaults filled in. It touches no key,
relay or network. A relative program is resolved against the file's own
directory, and a bare name is looked up on the `PATH`. A file that breaks
a rule is refused, exit 1, in one sentence naming the file, the route and
what is wrong. A channel `serve.json` serves cannot be a route's, and a
route on `default` is taken with a warning.

**`auu handle run` runs the routes.** Without `--once` it is the service:
rounds, with a hold on the relays between them for mail on the routes'
channels only, ended early when a retry or a reply falls due or an
operator's request lands, one run per home by its lock, exit 0 when
stopped and 4 when the keys lock under it. `--once` is one round. It
fetches, takes each ask on a route's channel into the ledger in the
inbox's order, leaves the asks a route's first round finds already waiting
unless `--backlog` says to run them, and runs each job's script: the
program and the file's own arguments, never through a shell and never with
a word of the message's, in an empty working directory of the attempt's
own, with the message as `message.json`, the body, a fresh copy of the
asker's files and `AUU_` variables, and a temporary directory of its own
named by `TMPDIR`. A parallel route runs up to its `max_parallel` jobs at
once, and no more than `workers_total` run across every route, the routes
offered a worker in turn. A job ends succeeded, failed for review, or
removed when the owner took the message back; a failure before the script
starts is tried again at serve's backoff. Each job that ends, succeeded or
failed for review, gets one reply on the ask's thread, its first line
saying how it ended and which attempt of how many, then the script's
`reply.txt` when it left one that holds to the text rule, and the files it
left in `output/attachments/` in name order, the text and the files held
together to the route's `max_reply_bytes`, each file under a name the
sender's rule takes and left out by name otherwise. The reply is sealed
once and kept where the script is not told, so a send that may have
reached the relay goes again as the same message; one that cannot be sent
is tried again up to the route's `retries`, and then said. The ledger
records the reply before the ask is marked read, and a succeeded job's
files go once its reply is saved. A started attempt that fails is in
review at once on a route that is not `idempotent`, since it may have done
its work, and is run again at serve's backoff up to the route's `retries`
on one that is. A stop kills the running script with everything it started
and writes its job interrupted before the run ends; a run that went away
leaves it for the next start to find. An interrupted job is run again only
on an idempotent route, and only when its script is known gone, by the
service's own stop or the host's `supervisor_reaps`.

**The operator's commands.** `auu handle status` says per route what the
ledger holds, the job in review that holds a sequential route by name, the
replies that could not be sent, and whether a service runs; `jobs` lists
the jobs in admission order and `inspect` shows one whole, with its logs'
first lines escaped. `retry` runs a failed job again, or sends again a
reply whose sends were spent; `skip` ends a job and sends its reply;
`pause` and `resume` hold and release a route's launches. Each changes the
ledger at once with no service running, and is queued under `handle/ops/`
for a running one, which applies it within a few seconds; a request that
will not read is moved aside and said. A retry of a job whose reply went
sends one more reply only if it then succeeds. A failure before a script
started names the home as `AUU_HOME` in the reply, never its path.

**Limits and cleanup.** A route takes asks up to its `max_queued` and
`max_queued_bytes`, the rest waiting in the inbox in their order and said
once a round; a script's logs are cut to `max_log_bytes` after its run,
the cut said; a failed or skipped job's directories go `keep_failed` after
it ended; and a sweep at the start and after every round removes only the
directories of the jobs the ledger names, saying anything else under
`handle/jobs/` or `handle/kept/` and leaving it.

**Serve and handle in one home.** `auu serve check` and `auu serve` now
read `handle.json` and refuse to serve a channel a route takes, naming
both files, as `auu handle check` and `auu handle run` refuse a route on a
channel `serve.json` serves. A reply to handle's own reply is nobody's
work, so no loop forms between the two.

**The record of handle's jobs and its rules.** `handle/ledger.json` is
the record of every job handle takes. It is held to its rules whenever it
is read: one that will not read or breaks a rule is refused by name, as
serve's ledger is, and never taken as a fresh start, and a job found
running is interrupted. `auu handle run` reads and writes it.

## After v0.19.0

Of what v0.19.0 left for a later release, this one closes:

- The tests' command runner read what a command printed only after the
  command returned, so a command printing more than the pipe holds waited
  for ever, and the reference, at 65,182 bytes, was 354 bytes short of
  Linux's 64 KiB (S71). The runner now reads while the command runs, so
  what a command prints to standard output may be any size.

## After this release

Left for a later release:

- The tests' other helpers that capture what a command prints read it only
  after the command returns, as the runner did before S71 (S77).
- Serve's filter of the API key variables from a handler's environment
  compares their names by case, which Windows does not, as handle's does
  now (S78).
- Each lock file has its holder's pid written into it by path after the
  lock is taken, not through the locked handle (S79).
- On Unix the group a script led is killed after it exits normally, and in
  the instant between the two its pid may be another program's (S80).
- A reply sent while a worker holds the ledger's lock delays the other
  workers' interrupted writes at a stop, so a service killed from outside
  just then leaves them in review rather than run again (S83).
- A script's logs are bounded only after it ends; a log bounded as it is
  written, a grace period at the stop, a retry-safe exit code such as 75,
  and a route handling more than one channel are left out of this version.
