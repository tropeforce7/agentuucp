# v0.20.0

v0.20.0 begins `auu handle`, a host's scripts run on the asks to a
channel; this version reads and checks its file and runs its routes a
round at a time, replying to each ask it handles. The wire level stays 2
and the relay's schema stays 13, so a v0.20.0 party and a v0.19.0 one are
the same party, and everything [`docs/releases/v0.18.0.md`](v0.18.0.md)
says about upgrading holds for v0.20.0 as it is.

## What changed

**`auu handle check` reads `handle.json` and says what it would run.**
`handle.json` in the home, or the file `--config` names, is a table of
routes keyed by id, each naming a channel and a command to run on the asks
that arrive there, with how it runs, its retries and its limits. `auu
handle check` holds the file to every rule
[`docs/handle.md`](../handle.md) gives and prints each route: its
channel, its command as written, its program as resolved, its jobs'
directory and its limits with the defaults filled in. It touches no key,
relay or network. A relative program is resolved against the file's own
directory, and a bare name is looked up on the `PATH`. A file that breaks
a rule is refused, exit 1, in one sentence naming the file, the route and
what is wrong. A channel `serve.json` serves cannot be a route's, and a
route on `default` is taken with a warning.

**`auu handle run --once` runs the routes a round at a time.** It fetches,
takes each ask on a route's channel into the ledger in the inbox's order,
leaves the asks a route's first round finds already waiting unless
`--backlog` says to run them, and runs each job's script: the program and
the file's own arguments, never through a shell and never with a word of
the message's, in an empty working directory of the attempt's own, with
the message as `message.json`, the body, a fresh copy of the asker's
files and `AUU_` variables, and a temporary directory of its own named by
`TMPDIR`. A job ends succeeded, failed for review, or removed when the
owner took the message back; a failure before the script starts is tried
again at serve's backoff. Each job that ends, succeeded or failed for
review, gets one reply on the ask's thread, its first line saying how it
ended and which attempt of how many, then the script's `reply.txt` when it
left one that holds to the text rule, and the files it left in
`output/attachments/` in name order, the text and the files held together
to the route's `max_reply_bytes`, each file under a name the sender's rule
takes and left out by name otherwise.
The reply is sealed once and kept where the script is not told, so a send
that may have reached the relay goes again as the same message; one that
cannot be sent is tried again up to the route's `retries`, and then said.
The ledger records the reply before the ask is marked read, and a
succeeded job's files go once its reply is saved.

**The record of handle's jobs and its rules.** `handle/ledger.json` is
the record of every job handle takes. It is held to its rules whenever it
is read: one that will not read or breaks a rule is refused by name, as
serve's ledger is, and never taken as a fresh start, and a job found
running is interrupted. `auu handle run` reads and writes it.

## After v0.19.0

Of what v0.19.0 left for a later release, this one closes:

- The tests' command runner read what a command printed only after the
  command returned, so a command printing more than the pipe holds waited
  for ever, and the reference, at 65,182 bytes, was 354 bytes short of
  Linux's 64 KiB (S71). The runner now reads while the command runs, so
  what a command prints to standard output may be any size.
