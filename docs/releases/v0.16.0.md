# v0.16.0

v0.16.0 sends one message to several people. It is the first release
after the floor, and it needs no upgrade order from v0.15.0: v0.15.0
reads every message it sends, a v0.15.0 relay carries it, and the
relay's storage is unchanged. The wire level stays 1 and the relay's
schema stays 13.

## What changed

**`--to` repeats, and takes a list.** `auu send --to bob --to carol` and
`auu send --to bob,carol` each send one message to both. Each recipient
is a name, a fingerprint, `self` or a bang path, resolved as a single
`--to` always was; one named twice is refused, and so is a list of more
than thirty-two, the protocol's ceiling, which is fixed for good. Every
copy is sealed for its own recipient, and every copy carries the same
list of everybody it went to, by fingerprint, inside its seal, in a
section called `recipients`.

**The relay holds a number of its own.** `max_recipients`, sixteen by
default and at most thirty-two, 0 meaning thirty-two, is the most
recipients a message to several may name on that relay. The relay says
the number in force in a section of its health answer and of
`auu-admin status`, `max-recipients`, rather than a field, so every
`auu` and `auu-admin` from v0.15.0 reads both answers still. A sender
asks it before anything is sealed and refuses a longer list, naming the
relay and the number. The relay holds the number itself where a request
has a body to carry the count, opening a stream and a user's forward,
and refuses a copy of a message to more with `413` and the code
`too-many-recipients`. A plain post's body is the envelope alone, so
there the setting binds an honest client and the post budget binds
every client.

**Every copy is sealed to the outbox first.** All the copies are sealed
and written to `outbox/` before any is posted, then posted in the order
given. The command ends with a line for each recipient and exits 2 when
any copy was not sent. A copy the relay refuses stays in the outbox with
the relay's code and words, and the rest go on; `auu send --resume` posts
it again, `auu outbox` lists what waits, and `auu outbox drop ID [PEER]`
gives one up. A send to several does not sleep through what it was told
to stop on: a relay asking this sender to wait more than a minute, a
copy over the sender's whole post budget, a relay refusing this machine
itself, or a copy that gets no answer stops the posting, with that copy
and the rest left in the outbox and `--resume` named. A copy that a
resume after a lost answer posts twice is delivered once to a machine
that still holds the first.

**A message to several says so.** `auu inbox` marks it `(to N)`, and
`auu read` prints a `to:` line naming everybody it went to. `--json`
carries `recipients` on a message to several, and `auu send --json`
gives it in place of `to`, which it gives only for a message to one.
`auu read` of one you sent says who has it, who does not yet, and which
copies you gave up.

**`auu reply --all`** answers the sender and every other recipient, as a
message to several of its own, or as an ordinary reply when that is one
person. `auu reply` still answers the sender alone. Every one of them
must be on your peer list: when one is not, the whole reply is refused
before anything is sealed, naming them. A follow-up on a thread whose latest message is your own message to
several takes `--to PEER`, one of its recipients, or `--all`.

**`auu serve`** hands its handler `AUU_RECIPIENTS`, everybody a message
to several went to, empty for a message to one. The expert still
answers the sender alone.

**A large message to several goes as one stream to each recipient.** A
message over 64 KiB travels as a stream; to several, every stream is
sealed to `outbox/` before the first upload, so the outbox holds the
payload once for each recipient until the uploads finish. A stream does
not cross a relay, so a recipient by bang path refuses the whole send.

## From v0.15.0

There is no order. Upgrade the relay and the clients in any order, one
at a time, and send from an upgraded machine at once.

A v0.15.0 `auu` reads a message to several, an envelope or a stream, as
a plain message from the sender to the reader. The `recipients` section
is not critical, so v0.15.0 passes over it, keeps it with the message,
and names it in `ignored_sections` in `auu read --json`; its `auu reply`
reaches the sender alone, since it has no `--all`. Nothing is kept as
`newer` or `malformed`.

A v0.15.0 relay takes a v0.16.0 sender's copies. A plain post carries
nothing new, and the count on a stream's open or a user's forward is a
section the v0.15.0 relay does not know and is not critical, so it is
ignored. That relay holds no `max_recipients`, and its health answer has
no `max-recipients` section, so a v0.16.0 `auu` holds itself to
thirty-two there.

A v0.15.0 `auu` and `auu-admin` against a v0.16.0 relay ignore the
`max-recipients` section on the health and status answers, and
everything else they send and read is as it was.

## From v0.14

Go straight to v0.16.0, in one step. v0.15.0 need never be installed:
the floor is the wire v0.15.0 set, and v0.16.0 speaks it. The order is
v0.15.0's, for the reasons
[`docs/releases/v0.15.0.md`](v0.15.0.md) gives, with one exception, a
large message to several, below. The relay's database is schema 13 on
v0.14, v0.15.0 and v0.16.0 alike.

**The relay first, with `auu-admin`,** if it is still on v0.14, since a
v0.16.0 `auu`, like v0.15.0's, refuses a v0.14 relay's health answer,
which lacks `wire_level`, and a v0.14 `auu-admin` misreads a v0.16.0
relay's answers about one mailbox and a newly added token as it does
v0.15.0's.

**Then each party, in turn, drains its inbox and upgrades.** Drain with
`auu inbox` while still on v0.14, then install v0.16.0.

**A party that has upgraded may send at once,** except a large message
to several to anybody still on v0.14. v0.14 reads a stream's manifest
strictly, so it refuses one that carries a section, as every stream to
several does: it keeps the manifest under `damaged/` as malformed,
acknowledges it, so it is gone from the relay, and says to ask the
sender to send it again. Send that once the recipient has upgraded.
Every other message v0.14 reads as it reads v0.15.0's, and a message to
several that is not a stream reads there as a plain message from the
sender.

**A party still on v0.14 holds its sends** to anyone who may have
upgraded, until it has upgraded too. v0.16.0, like v0.15.0, refuses a
message v0.14 sealed as malformed, saying "the sealed record carries no
version".

**A message refused in the window** is not lost. The machine that
refused it keeps it under `damaged/`, and it is sent again once its
sender has upgraded, or, for a large message to several, once its
recipient has.
