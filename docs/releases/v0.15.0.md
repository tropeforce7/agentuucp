# v0.15.0

v0.15.0 is the floor. Everything that speaks the wire, every relay and
every `auu`, goes to it once, together, and from then on versions may
differ. v0.14.0 and before are not supported.

## What changed

Until now a newer build could not add anything an older one would not
misread or refuse at random. From this release there is one place for it,
`sections`: a message, a stream's manifest, every answer a relay gives and
every request it is sent carries a list of named parts, and a reader that
does not know a part ignores it, or, when the sender marked it critical,
refuses the whole thing by name and says that a newer `auu` is needed.
Nothing is ever read with a part silently dropped. A relay carries an
envelope whose version it does not know, since what the version means is
between the sender and the recipient. A relay says what it can do as
`wire_level` on its health answer. And every refusal a relay gives carries
a code, which `auu` decides on instead of the words, so a relay may change
its words and add codes without any `auu` misreading them.

The break with v0.14.0 runs one way. A v0.15.0 `auu` writes no sections,
so every message it sends is one a v0.14.0 machine opens and reads as
usual. But v0.14.0 seals a message without the version v0.15.0 reads
inside the seal, and v0.15.0 refuses such a message as malformed, saying
"the sealed record carries no version", and keeps it under `damaged/`.
Streams, the way a message over 64 KiB travels, are unaffected either
way: both builds read the other's. So the upgrade is done in an order.

## The order

**The relay first, with `auu-admin`.** A v0.15.0 `auu` requires the wire
level on the relay's health answer, which it asks before its first
listing, and a code on every refusal, and refuses a v0.14.0 relay's health
answer and refusals by name. Upgrade the relay before any client, and
`auu-admin` with it: a v0.15.0 relay wraps its answers about one mailbox
and a newly added token, which a v0.14.0 `auu-admin` misreads.

**Then each party, in turn, drains its inbox and upgrades.** Drain first,
while still on v0.14.0: `auu inbox` fetches and reads everything waiting,
so nothing a peer sealed with v0.14.0 is left on the relay for the new
build to refuse. Then upgrade.

**A party that has upgraded may send at once,** since v0.14.0 reads
v0.15.0's ordinary mail.

**A party still on v0.14.0 holds its sends** to anyone who may have
upgraded, until it has upgraded too. That is where the window is: a
message from v0.14.0 to a machine already on v0.15.0 is refused there.

**A message refused in the window** is not lost. The machine that refused
it keeps it under `damaged/`, and its sender sends it again once upgraded.

**What a machine left behind says.** A v0.14.0 machine reads what v0.15.0
sends it. What it cannot read is a message carrying a part its sender
marked critical, or a stream carrying a part of any kind, since v0.14.0
reads a stream's manifest strictly. No v0.15.0 command sends either, and a
later build may: v0.14.0 shows such a one as `malformed` and advises
asking the sender to send it again.
That advice is wrong, since the message is sound and the reader too old
for it. It is the best a binary that has already shipped can do, and one
upgrade ends it, since from v0.15.0 a reader knows the door and says
"needs a newer auu" instead.

After this release, an upgrade needs no order. A newer build's additions
reach an older one as sections it ignores, refusals it shows in the
relay's own words, or a critical part it refuses by name with the advice
to update.
