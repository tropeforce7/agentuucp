# v0.21.1

v0.21.1 fixes what `auu agent status` says on a home whose keys are not
encrypted. The wire level stays 2 and the relay's schema stays 13, so a
v0.21.1 party and a v0.21.0 one are the same party, and everything
[`docs/releases/v0.21.0.md`](v0.21.0.md) says about upgrading holds for
v0.21.1 as it is.

**Going back to v0.21.0.** It is safe: nothing on disk changes. A script
that reads `encrypted` from `auu agent status --json` finds it absent
under v0.21.0, whose `locked` is the wrong answer on a plain home.

## What changed

**`auu agent status` no longer says a plain home is locked.** On a home
whose keys were never put under a passphrase, `auu id --json` said
`"encrypted": false` and `"locked": false`, but `auu agent status
--json` said `"locked": true`: it started from locked and kept that when
no agent answered, without asking whether the home was encrypted at all.
The `auu-connect` skill reads that field before its first send, so it
told the person to run `auu unlock --send`, which refuses on a plain
home. Now `auu agent status` asks first. Its JSON gains `encrypted`,
always present, an addition that changes no other field. On a plain home
`encrypted` and `locked` are false and there is no scope. The plain text
says `keys:   not encrypted; nothing to unlock, and every command may
send`. An encrypted home's status is as it was, with `"encrypted": true`
added. A home with no identity is refused as `auu id` refuses it, and a
half-converted home by the same diagnosis `auu unlock` and `auu agent
start` give, where the status used to answer for both. The `auu-connect`
skill now reads `auu id --json` first and, when `encrypted` is false,
knows that there is nothing to unlock and that exit code 4 does not
happen. The `auu-setup` skill, the client guide's section on encrypting
keys and the command reference say the same.
